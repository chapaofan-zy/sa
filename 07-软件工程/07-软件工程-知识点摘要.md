## 软件产品线

| 关键词 | 一句话概括 |
| --- | --- |
| 软件产品线 | 通过共性与可变资产配置，快速生成相似产品。 |
| 共性部分 | 多个产品共同需要功能、架构、组件、接口和测试用例。 |
| 可变部分 | 产品差异通过功能或配置表达。 |
| 产品生成 | 从共性资产中选择并配置可变部分形成具体产品。 |
| 产品线收益 | 提高复用率，降低成本，缩短上市时间并保持质量一致。 |
| 产品线风险 | 前期投入和可变性管理复杂，共性设计失误会影响全线。 |
| 演化方式 | 从已有系统逐步提取资产并建设产品线。 |
| 革命方式 | 从一开始统一规划架构、共性资产和可变性。 |
| 基于现有产品 | 从旧产品提取共性资产，初期成本和风险相对较低。 |
| 开发全新产品线 | 从领域分析和参考架构开始建设，前期投入较大。 |
| 建立方式区别 | 演化和现有产品偏渐进，全新产品线和革命偏整体规划。 |
| 分类关系 | 两组建立方式的层级关系在教材中存在待验证表述。 |

## 软件开发方法与模型

### 软件开发过程模型

| 关键词 | 一句话概括 |
| --- | --- |
| 瀑布模型 | 按需求、设计、编码、测试和维护顺序推进，适合稳定需求。 |
| 演化模型 | 先交付可运行初版，再依据反馈持续修改完善。 |
| 螺旋模型 | 每轮迭代都进行风险分析，适合大型高风险项目。 |
| 喷泉模型 | 允许设计、编码和测试交叉重叠，常用于面向对象开发。 |
| 变换模型 | 将形式化规格逐步变换为程序实现，强调正确性。 |
| 智能模型 | 用人工智能、知识库和自动推理辅助或自动完成开发。 |
| V 模型 | 将开发阶段与对应测试阶段关联，强调测试前移。 |
| 验证与确认 | 验证关注是否正确构造软件，确认关注是否构造正确软件。 |
| 模型辨析 | 瀑布重顺序，演化重迭代，螺旋重风险，喷泉重交叉。 |

### 快速应用开发（RAD）

| 关键词 | 一句话概括 |
| --- | --- |
| RAD 定义 | 以快速构建、持续迭代和用户参与为核心的开发方法。 |
| RAD 核心 | 通过原型、反馈、现成组件和工具缩短交付周期。 |
| RAD 特点 | 原型驱动、用户参与、迭代开发、组件复用并强调速度。 |
| RAD 流程 | 业务建模、数据建模、过程建模、应用生成、测试交付。 |
| RAD 优点 | 周期短、反馈早、匹配业务并能适应需求变化。 |
| RAD 局限 | 依赖用户、工具和团队能力，不适合超大复杂系统。 |
| RAD 适用场景 | 适合中小型业务系统、Web 应用和快速验证项目。 |
| RAD 侧重点 | 偏重原型、工具、组件复用和过程效率，不等同于敏捷。 |

### 敏捷开发

| 关键词 | 一句话概括 |
| --- | --- |
| 敏捷开发 | 以用户价值为核心，通过短迭代和反馈持续交付价值。 |
| 敏捷价值观 | 个体互动、可工作软件、客户合作和响应变化更重要。 |
| 敏捷特征 | 迭代增量、持续反馈、拥抱变化、持续集成和自组织。 |
| 迭代增量 | 每轮完成可运行、可验证或可交付的软件增量。 |
| 演化与敏捷 | 演化组织生命周期，敏捷强调价值观、协作和持续交付。 |
| RAD 与敏捷 | RAD重快速构建，敏捷重响应变化、协作和持续改进。 |
| Scrum | 以固定 Sprint、角色、事件和产品增量组织迭代。 |
| Scrum 角色 | 产品负责人定目标，Scrum Master促协作，团队交付。 |
| Scrum 事件 | 计划、每日站会、评审和回顾支撑每轮迭代。 |
| Scrum 产物 | 产品待办、Sprint待办和产品增量记录需求、任务与交付。 |
| DSDM | 固定时间、成本和资源，通过调整范围保证按时交付。 |
| MoSCoW | 将需求分为必须、应该、可以和本次不做四类。 |
| XP | 通过严格工程实践提高质量并应对快速变化。 |
| XP 实践 | TDD、结对编程、持续集成、重构、小发布和现场客户。 |
| Scrum 与 XP | Scrum偏项目管理，XP偏编码、测试和持续集成。 |
| Crystal | 按团队规模、项目风险和关键程度裁剪流程。 |
| Kanban | 通过可视化、限制WIP和拉动式开发改善任务流动。 |
| FDD | 以用户可感知功能为单位，建模、计划、设计并构建。 |
| ASD | 以猜测、合作、学习三个阶段适应复杂性和不确定性。 |
| Lean | 消除浪费、内建质量、快速交付并优化整体价值流。 |
| AUP | 保留统一过程基本活动，以短迭代和轻量流程敏捷化。 |
| SAFe | 面向大型组织和多团队，统一规划并支持规模化交付。 |
| 方法辨析 | Scrum管项目，XP管技术，Kanban和FDD重交付。 |

### 统一软件开发过程（RUP）

| 关键词 | 一句话概括 |
| --- | --- |
| RUP 定义 | 规定阶段、角色、活动、制品和工作流的迭代过程框架。 |
| RUP 核心 | 用例驱动、架构中心、迭代增量和风险驱动。 |
| 初始阶段 | 明确目标、范围、可行性、用例、风险和初步计划。 |
| 细化阶段 | 完善需求、确定基线架构并解决主要技术风险。 |
| 构造阶段 | 详细设计、编码集成、测试并形成可运行版本。 |
| 移交阶段 | 部署、培训、试运行、修复缺陷并正式发布。 |
| RUP 工程流 | 业务建模、需求、分析设计、实现、测试和部署。 |
| RUP 支持流 | 项目管理、配置变更管理和环境工作流贯穿各阶段。 |
| RUP 迭代 | 每次迭代都完成部分分析、设计、实现和测试。 |
| RUP 与演化 | RUP具有演化特征，但演化模型不等于RUP。 |
| RUP 与螺旋 | RUP重用例和架构，螺旋重每轮风险分析。 |
| RUP 局限 | 过程和文档较复杂，小项目使用时需要裁剪。 |

## 软件开发环境与工具

| 关键词 | 一句话概括 |
| --- | --- |
| 三类工具 | 软件工具分为开发工具、维护工具和管理支持工具。 |
| 软件开发工具 | 辅助需求、设计、编码、测试和发布新系统。 |
| 软件维护工具 | 支持交付后修复、修改、改进和环境适应。 |
| 维护类型 | 维护包括改正性、适应性、完善性和预防性维护。 |
| 管理支持工具 | 支持计划、协作、配置、质量、风险和过程管理。 |
| 工具分类边界 | 同一工具可跨类使用，分类取决于实际用途。 |
| Git | 可兼属开发版本控制、维护变更管理和支持配置管理。 |
| Jira | 主要用于项目任务管理，也支持缺陷、需求和测试管理。 |
| Jenkins | 支持持续集成构建，也可用于发布和回归测试。 |
| IDE | 主要用于开发，并支持维护中的调试、重构和代码分析。 |
| 工具记忆 | 开发工具造软件，维护工具修软件，管理工具管项目。 |

## 软件形式化方法

| 关键词 | 一句话概括 |
| --- | --- |
| 形式化方法 | 使用严格数学语言描述、设计和验证软件。 |
| 形式化思路 | 用数学模型描述需求，通过推理验证并尽早发现错误。 |
| 形式化特点 | 严谨且适合高可靠系统，但学习和使用成本较高。 |
| 净室软件工程 | 以形式化规格、严格评审和统计质量控制预防缺陷。 |
| 两者区别 | 形式化方法重数学证明，净室工程重流程预防和统计控制。 |

## 软件过程管理

| 关键词 | 一句话概括 |
| --- | --- |
| CMM 一级 | 初始级过程混乱无序，项目结果依赖个人和临时应对。 |
| CMM 二级 | 可重复级建立项目管理纪律，包含六个关键过程域。 |
| 二级过程域 | 需求、计划、跟踪、子合同、质量保证和配置管理。 |
| CMM 三级 | 已定义级建立组织标准过程，项目可裁剪实施。 |
| 三级过程域 | 组织焦点、定义、培训、集成、产品工程、组间协调、同行评审。 |
| CMM 四级 | 已管理级用定量和统计方法控制过程与产品质量。 |
| 四级过程域 | 定量过程管理和软件质量管理。 |
| CMM 五级 | 优化级通过缺陷预防、技术和过程变更持续改进。 |
| 五级过程域 | 缺陷预防、技术变更管理和过程变更管理。 |
| CMM 等级记忆 | 一乱、二复、三定、四量、五优。 |
| CMM 过程域总数 | 二至五级关键过程域合计十八个。 |
| CMMI 等级 | CMMI五级为初始、管理、定义、量化管理和优化。 |
| 评估对象 | CMM和CMMI主要评估组织过程能力，不是个人或单项成果。 |
| CMM 评估流程 | 建组、问卷、分析KPA、现场调查、汇总发现、绘制剖面图。 |
| 评估易错点 | 第六步是绘制KPA剖面图，不是单列报告评估结果。 |
| CMM 演变 | CMM较早，后来逐渐由CMMI取代但考试仍常考CMM五级。 |

## 软件重用和再工程

### 软件再工程

| 关键词 | 一句话概括 |
| --- | --- |
| 软件再工程 | 以旧系统为基础分析、改造和迁移，同时保留业务价值。 |
| 再工程目的 | 延长寿命，降低维护升级成本并适应新环境和需求。 |
| 再工程过程 | 逆向分析、重构重组、正向工程以及迁移转换。 |
| 再工程与新开发 | 再工程利用旧资产改造，全新开发从零设计建设。 |

### 软件逆向工程

| 关键词 | 一句话概括 |
| --- | --- |
| 逆向工程 | 从程序、行为和数据推导功能、结构、算法及接口。 |
| 静态分析 | 不运行程序，分析文件、指令、函数、字符串和控制数据流。 |
| 动态分析 | 运行程序，观察输入输出、调用、状态和运行时行为。 |
| 动静结合 | 先静态定位关键位置，再动态观察并回到代码确认逻辑。 |
| 信息交换模型 | 信息经过输入、解析、内部处理、封装和输出到达接收方。 |
| 交换分析内容 | 分析参与者、接口、数据格式、流向、状态、异常和重试。 |
| 逆向分析手段 | 可记录输入输出、监控活动、跟踪API、断点和构造测试输入。 |
| 反汇编 | 将机器码转换为汇编指令，便于精确跟踪底层执行。 |
| 反汇编局限 | 变量名、类型、注释等语义丢失，混淆和优化会增加难度。 |
| 反编译 | 将机器码或中间代码推测为高级语言伪代码。 |
| 反编译局限 | 类型和控制结构可能错误，结果不等于原始源代码。 |
| 反汇编与反编译 | 前者输出低层汇编且较准确，后者输出高层伪代码但需推测。 |
| 逆向分析流程 | 目标与环境、格式架构、静态分析、反汇编反编译、动态验证。 |

### 软件重用过程

| 关键词 | 一句话概括 |
| --- | --- |
| 软件重用 | 既构建可复用构件，也检索评价并使用已有构件。 |
| 面向复用开发 | 构件不仅满足当前需求，还要考虑跨系统复用。 |
| 重用收益 | 提高通用性和质量，降低后续成本并扩充组织资产库。 |
| 构件构建流程 | 领域分析、构件设计、实现测试、认证、入库、发布维护。 |
| 构件要求 | 高内聚、低耦合、接口清晰、可配置，并具备文档和认证。 |
| 实例重用 | 通过组合和委托直接调用已有对象，表达has-a关系。 |
| 继承重用 | 子类复用并扩展父类，表达is-a关系但耦合较高。 |
| 多态重用 | 面向统一接口编程，使同一调用对应多种实现。 |
| 组合优先 | 仅相似功能而无合理父子关系时，应优先组合或接口。 |
| 三种重用区别 | 实例靠组合，继承靠父子，多态靠抽象接口和动态绑定。 |
