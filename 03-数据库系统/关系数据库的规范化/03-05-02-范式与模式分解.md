# 范式与模式分解

---

## 范式概览

讲义列举 1NF、2NF、3NF、BCNF、4NF 和 5NF，并指出实际应用中通常达到 3NF。范式越高，对依赖关系和数据冗余的约束通常越严格，但分解关系也可能增加查询组合的复杂度。

## 第一范式（1NF）

关系模式中所有属性只包含原子值，即每个分量都是不可再分的数据项，称为满足 1NF。

如果一个字段中保存多个值或一组重复数据，通常说明它不满足原子性要求。

## 第二范式（2NF）

关系模式满足 1NF，且每个非键属性都完全依赖于候选键，则满足 2NF。

例如关系模式 `(A, B, C, D)` 中：

```text
(A, B) -> C
B -> D
```

如果 `(A, B)` 是候选键，那么 B -> D 构成 D 对组合键的部分函数依赖，关系不满足 2NF。讲义给出的分解是：

```text
SC1(A, B, C)
SC2(B, D)
```

## 第三范式（3NF）

关系模式满足 2NF，并且消除了非键属性对候选键的传递依赖，则满足 3NF。

例如学生关系中，学号决定所在系，所在系又决定系名称和系地址，就可能出现非主属性通过中间属性传递依赖学号的情况。

## BCNF

讲义给出的判断要点包括：

- 非主属性对每个码完全函数依赖。
- 主属性对不包含它的码完全函数依赖。
- 不存在属性完全函数依赖于非码属性组的情况。

仓库管理关系的例子说明：一个关系可能满足 3NF，但由于存在“仓库号决定管理员号、管理员号决定仓库号”等决定关系，仍可能不满足 BCNF。

讲义对 BCNF 的文字定义较简略，本文按例题整理，具体判断时应以候选键和函数依赖集合为准，相关表述**待验证**。

## 第四范式（4NF）

4NF 是 BCNF 针对多值依赖的推广。

如果对于关系中的 X、Y，X 能决定一组与其他属性无关的 Y 值，记为：

```text
X ->> Y
```

当关系中存在多值依赖时，若 X 不包含候选键，可能产生冗余。讲义用分解关系消除这种多值依赖。

## 模式分解

存在修改异常时，可以将一个关系模式分解为多个子关系模式。分解时需要考虑：

- 是否保持函数依赖。
- 是否为无损联接分解。

### 无损联接的讲义判断法

若两个子关系的交集能够函数确定其中一个关系的差集，例如：

```text
R1 ∩ R2 -> R1 - R2
```

或：

```text
R1 ∩ R2 -> R2 - R1
```

则讲义认为该分解是无损的。

### 保持函数依赖

分解后仍能保留原函数依赖集中的全部约束。如果原函数依赖在分解后的某个关系上仍然成立，则该依赖得到保留；讲义将此作为充分条件。
